# The fwos CLI

`fwos` means `node "${CLAUDE_PLUGIN_ROOT}/dist/fwos.mjs"` inside Claude Code. In a terminal or CI it
is the app's own copy, run with `pnpm exec fwos`: in an app `/fwos:start` made, the scaffold vendored
it into `.fwos/cli/`, and any other app does the same from a clone of this repository
(`node <clone>/plugin/dist/fwos.mjs vendor`, then `pnpm add -D file:.fwos/cli`). Same file, same
results. Exit codes: 0 ok, 1 a check failed, 2 usage or input error (an unknown command,
check id or flag, a `--dir` that isn't a folder). Each command takes only its own flags plus
`--dir`, so a typo such as `--jsn` exits 2 instead of being ignored. Add `--json` to `adopt`,
`check`, `report`, `status`, `next`, `doctor`, `change list`, `change map`, `change drift`, `change trace`, `tests run`,
`tests status`, `slice drift`, `harness status`, `ia diff`, `prototype check` and `prototype diff` for machine-readable output (`harness targets`
and `harness record` always answer in JSON). `fwos <command> --help` (or `fwos help <command>`) prints that command's
usage and runs nothing, `fwos help` prints every command, `--version` prints the version, and
`fwos doctor` lists every check id.
`check --staged` fails closed when disk differs from the commit (a staged file with unstaged edits,
or a file the commit deletes that is still on disk), because the checks read the files on disk.

| Command | What it does |
|---|---|
| `fwos init [--platforms web] [--mode new\|adopt\|spike] [--name "<app>"]` | Step 0: creates `.fwos/` and change `0001-initial`. `--mode adopt` sets up an existing app at level checks with no proposal; `fwos adopt` shows what it finds first. `--mode spike` is throwaway: no approvals and no checks, so `fwos check` (`--staged` too) and `fwos report` print NOT VERIFIED (spike mode) and exit 1 |
| `fwos adopt [--app <dir>] [--level checks\|design\|delivery] [--docs <dir>] [--design-system <dir>] [--name "<app>"] [--yes]` | Reads an existing Next.js app and prints a proposal, writing nothing: each finding with the file it came from, what wasn't found, what fwos would reuse, add and change, the `.fwos/state.json` it would write, the hook and CI previews, the checks that would run and the capabilities of each level. The preview exits 1 when there's no app it can adopt; `--yes` refuses unsupported input with exit 2 and an error on stderr. A monorepo with several Next.js apps needs `--app`. `--yes` does it (`.fwos/`, the `.gitignore` line, the baseline, and at level design the app's own theme as tokens), and refuses while a decision is open. On an adopted app, `--level` changes the level and keeps every record; a higher level takes the findings of the checks it turns on into the baseline. The proposal, and `fwos status`, show the six stages (idea, design, spec, test-plan, build, acceptance), each with what the team does there today and the file it was read from, the gap fwos addresses, what it adds and the evidence that would show it helped |
| `fwos adopt --keep <stage>[,<stage>] --reason "<why>"`, `fwos adopt --use <stage>[,<stage>]` | Keeps the team's own practice for a stage it already serves well, recorded with why in `adopt.keep`; `--use` gives it back. Previews, then `--yes`. A kept stage gets nothing from fwos: idea needs no `## Request`, design no `## States`, spec only the criteria with their `- Source:`, test-plan turns `tests/plan` and `tests/regression` off and approves the spec alone, build lifts the spec gate and the map's hold on `change done`, and acceptance closes the change on the team's linked sign-off instead of `fwos approve acceptance`. It changes no level, record or baseline |
| `fwos next --json` | The current change, its step, what blocks it, the skill to load and one sentence of what to do. For an adopted app's change, `workflow` too: the branch named as the team's are, their PR template and CODEOWNERS; `open`, what it carries into its next step (open questions, assumptions, dropped asks and criteria, kept stages with nothing linked); and the stages the team keeps in `adopt.keep` |
| `fwos status [--json]` | Approvals (approved, stale, missing, skipped), stale docs, locked tests, spend |
| `fwos check [ids...] [--staged]` | Every check as PASS, FAIL or OFF with the reason. `ids` narrow it (`walls`, `design-system`) |
| `fwos report` | Runs every check and writes `docs/app/reports/acceptance.md` from the evidence |
| `fwos doctor [--json]` | Tools, platforms, adapters at 3 levels, every check on or off and why. It reads only, so the verify driver is installed at most |
| `fwos doctor --start [--url <url>] [--json]` | Doctor, and before it calls the verify driver active, it starts the app (`next dev` on a free port, with the screens browser on) or uses the one at `--url`, renders the first state fixture `fwos harness targets states` lists in Chromium through the app's own Playwright, opens `/` as the first role in ia.json through the IA harness's test identity, and stops what it started. Active, the row names what rendered and the defects that lets fwos's harness catch: only those the declared states can show, and the IA ones only when the app took the test identity. Anything that doesn't start or render is named, and the driver stays inactive |
| `fwos approve <target> --by "<name>" [--via chat\|pr\|autopilot] [--ref <review URL>]` | Records a human approval as content hashes. `--via pr` needs `--ref`, the review the yes was given in. In an adopted app only a change's own `spec` (once the change is mapped, and with every `### Q-<n>` answered) and `acceptance` are approved, and only inside a change, plus `fidelity`, which reviews fwos's import of the team's design system. The spec's approval says what the change carries into the build |
| `fwos skip <target> --reason "<why>" --by "<name>"` | Skips research, architecture, design-system or screens; logged. Not in an adopted app, whose change starts at its spec |
| `fwos step <step>` | Moves the current change; going forward needs every earlier approval. Into the build or acceptance, an adopted app's change says what it carries: open questions, assumptions, dropped asks and criteria, kept stages with nothing linked |
| `fwos change new "<request>" --route <route> [--link <url\|path>]` | Starts a change at the route's entry step. It becomes the current change, and the command names any earlier change still open. `--link` (repeatable) records an issue or doc URL, or a project file with its hash, as the change's context; with a link the request text is optional. In an adopted app it needs level delivery, and only `code-only` (build) and `touches-ac`, `new-feature` and `data-change` (spec) exist |
| `fwos change map <route\|file>...` | Adopted app: what the open change touches, read from the code (a route by its URL, a file by its path): the page and the route files around it, every file they import, the app's UI components, the API routes and server actions they call, the existing tests that import the page or visit the route, and the code owners. Recorded on the change. The spec's approval waits for it, `spec/format` asks the Context to name each mapped file, and `tests/plan` the regression scope to name each test it found |
| `fwos change drift` | Adopted app: the open change's edits since it began against its map. An existing source file it edited outside the map exits 1, naming the `fwos change map` that takes it in. New files, tests, docs and configs are the change's own |
| `fwos change link <url\|path>... [--stage <stage>]` | Links what the open change builds on, in place and never copied: a URL, or a project file with its hash. With `--stage`, the link is the team's own artifact for that stage of the change (its design, its test plan, the sign-off its acceptance got), which is how a kept stage hands its work to fwos |
| `fwos change trace [<id>] [--json]` | Adopted app: a change (the latest by default) from its request to its evidence: its links, who served each stage, each ask and the criteria that deliver it, the questions and their answers, the states, each criterion's cases (whether the app's scripts can run them) and verdict, the regression scope as it last ran, the build's edits against the map, and what is still open |
| `fwos change cursor --section <s> --pending Q-1,Q-2` | Records where you stopped, for resuming |
| `fwos change spend --step <step> --usd <n>` | Adds spend (a positive number of dollars) to the current change |
| `fwos change list [--json]`, `fwos change show [<id>]` | Every change with its step and status; one change as JSON |
| `fwos change done` | Closes the change (checks must pass; acceptance approved unless code-only; in an adopted app, no edit outside what it maps). In an adopted app that keeps its own acceptance, the team's sign-off linked with `--stage acceptance` stands for the approval, and one that keeps the build isn't held to the map |
| `fwos stamp <doc> --from brief.md,ia.json` | Writes `based_on` hashes into a doc's front matter |
| `fwos design-system init [--from-shadcn <globals.css>] [--name "<n>"]` | Writes `design-system/` from the starter or a shadcn theme. From a theme it keeps a copy in `design-system/source/` and writes the mapping report |
| `fwos design-system report [--json]` | Writes `docs/app/reports/design-system.md`: every slot with the source file and key it reads, its original and resulting value in each mode and its status, what the source had that nothing took, each component with its variants, states and interactions, and the last rendered comparison. Prints token validity, generated CSS, adoption coverage and fidelity as separate outcomes, with the fidelity approval beside them |
| `fwos design-system gallery` | Writes a dev-only route at `/fwos-screens/fwos-gallery` and a Playwright runner into the app (generated, and skipped by every check), and prints the command that compares the original and adopted side of every component in both modes at 390 and 1280 pixels wide. The run writes `.fwos/local/results/fidelity.json` and screenshots in `.fwos/local/gallery/`. Refuses the neutral starter, which has no source to compare |
| `fwos design-system decide <item...> --as replace\|omit\|intentional --reason "<why>" --by "<name>"` | Records a decision in `.fwos/fidelity.json` about a row, a component or `render:<component>`, or about every undecided item of a status (`defaulted`) the decision fits. A token takes `intentional`, a component `replace` or `omit`. A decision covers what it saw: when that changes, it is undecided again |
| `fwos tokens build [--check]` | Generates CSS variables and the Tailwind theme from the tokens, both or neither: it writes nothing while one was edited by hand. `--check` writes nothing and exits 1 when they differ from the tokens |
| `fwos contract mocks [--check]` | Generates the fail-closed mock fetch from `openapi.yaml` and fixtures. `--check` writes nothing and exits 1 when it differs from them, as the `architecture/mocks` check in `fwos check` does |
| `fwos scaffold web [--name "<app>"] [--fwos-check <spec>]` | The walking skeleton; never overwrites a file. It copies this CLI into `.fwos/cli/` and pins `fwos-check` to `file:.fwos/cli`, so install and CI need nothing else. `--fwos-check <spec>` pins something else instead (for example `link:<path>` for a local checkout, or a GitHub Release tarball) and skips the copy. A pin the project already has wins |
| `fwos vendor` | Refreshes `.fwos/cli/` to this plugin's version after an update, and touches nothing else (running the scaffold again would also restore template files you deleted). It removes a file this version no longer ships, and copies each file it replaces or removes to `.fwos/local/backup/<time>/` first. It writes nothing while a file there was edited since fwos wrote it, or fwos didn't write one where the copy reads its bundle, rules, starter or templates, and names each. Refuses when the project pins `fwos-check` to something else |
| `fwos update [--yes]` | After a plugin update. Reads the schema of every pack file (`design-system.json`, `components.json`, `rules.yaml`, `ia.json`, `modules.json`) and record in `.fwos/`, then previews what it would do, writing nothing: a file it migrates from an older schema, and what it replaces, adds or removes in `.fwos/cli/` (as `fwos vendor`, when the project pins `fwos-check` to the copy). `--yes` does it, after copying each of those files to `.fwos/local/backup/<time>/`. It writes nothing and exits 2 while anything is in the way: a file from a newer schema (upgrade fwos), an older one it has no migration for (rewrite it as the schema this fwos reads), or a patched file in `.fwos/cli/`. This release has no migration to run: every pack file and record is still at its first schema |
| `fwos harness [--check]` | Writes fwos's own Playwright tests into the app's `e2e/` folder: `fwos-states.spec.ts` renders every page and component state fixture where the app renders it (the screens browser, or for a component in an app without it the comparison gallery) and hovers and clicks whatever looks clickable, `fwos-ia.spec.ts` opens every static route as each role and flag setting and reads the nav (with no ia.json it runs nothing). They are fwos's files (`state/owned` catches an edit), and the scaffold writes them too. Refuses to overwrite one you edited. `--check` writes nothing and exits 1 naming a missing or edited one |
| `fwos harness targets <states\|ia>`, `fwos harness record <states\|ia> <target> --revision <rev>` | What the harness runs: `targets` lists what it renders or opens (for states, the path that renders each one, or null when nothing in the app does), with the revision the run starts on, and `record` keeps what one test saw (JSON on stdin) in `.fwos/local/runs/`, tied to the code it ran on, and answers with what breaks the contract. The harness calls both; you don't need to |
| `fwos harness status [--json]` | Each run record, and whether it still counts: it doesn't once the code changes, or when a harness other than this fwos version's recorded it |
| `fwos codex agents` | Writes fwos's agents for Codex to `.codex/agents/fwos-*.toml`, generated from the plugin's own agent files with this machine's plugin folder, and git-ignores them. `fwos init` does it when it runs inside Codex. Run it again after a plugin update; `fwos doctor` says when they're out of date. Refuses to replace a file fwos didn't write |
| `fwos ia diff [--base <ref> \| --from <file>]` | What changed in `ia.json` since a git ref (default `HEAD`) or another file, per page, role and flag. It compares two versions of `ia.json`, not the app: `fwos prototype diff` compares an intended IA with the app |
| `fwos prototype check [<id>] [--json]` | Each prototype bundle (`docs/app/prototypes/<id>/bundle.json`): what stops it being promoted, and whether its promotion still holds. A bundle links a visual artifact from any tool, a real-component companion for each page it covers, a state inventory, the build spec, the decision record when there is one, and the intended `ia.json`. It's refused for a link into a `working/` folder (in the bundle or in a page it links), a missing file or heading, a role or flag the project's `ia.json` lacks, a duplicate ID, an invalid IA, an inventory that doesn't list exactly each page's states, a page with no companion, or an app route the intended IA neither lists nor marks unlinked. A promoted bundle whose pinned inputs changed is stale. Exits 1 on either |
| `fwos prototype promote <id> --by "<name>"` | Pins the bundle's inputs by hash in `.fwos/prototypes.json` (a shared doc by its linked section or decision row, so an edit elsewhere in it doesn't count). Refuses while `prototype check` finds a problem, outside a git repository, or while an input isn't committed as it is |
| `fwos prototype diff <id> [--json]` | The bundle's intended IA against the app, by stable page ID: a page the app lacks (added), at another route (moved), one the intent hides from a role the app shows it to (hidden) or the reverse (exposed), a nav that differs, and an app route the intent doesn't classify. Routes come from the app's code, who sees what from fresh runs of fwos's IA harness; a role and flag setting no run covered is named as not compared |
| `fwos tests run [<script>...]` | Runs the project's test scripts (`test`, `test:*`, `e2e`, `e2e:*`, or the ones named) through its package manager, as the team does, with a JUnit reporter added on the command line for Vitest, Playwright, Jest (its JSON, turned into JUnit), Cypress and Mocha. Results go to `.fwos/local/results/` and each run to `.fwos/local/runs/tests/`, which counts at acceptance only while application/test inputs and exact result bytes still match the run, with the team's configs left as they are. Any other runner, or a script that chains commands, runs as it is and says its run proves nothing. Watch and UI scripts are skipped, and a script that only runs others runs as those others. Exits 1 when a script fails |
| `fwos tests lock <files> --red\|--existing [--slice S1]` | Locks a slice's tests by hash (red: they failed first). In an adopted app only inside a change, and only files it added or changed since it began |
| `fwos tests status` | Each locked test: ok, changed, missing or unlocked |
| `fwos tests unlock <file> --reason "<why>" --reviewer "<name>"` | Records an unlock; then edit and lock again |
| `fwos slice drift <S1> [--base <ref>]` | Files changed outside the slice's modules, and undecided new dependencies |
| `fwos signoff <AC-x-n\|GAP-n> --by "<name>" [--note "..."]` | A named sign-off for a manual check or a gap. The id must be an AC with a `Manual:` line in `spec.md` or a gap `test-plan.md` names; any other id exits 2, an AC its tests prove included |
| `fwos spike new <name>` | Throwaway code in `spikes/` |
| `fwos git-hook install` | Runs `fwos check --staged` before each commit. The hook goes where git runs hooks (`git rev-parse --git-path hooks`: `core.hooksPath`, or the main repository's hooks from a linked worktree), and for a project in a subfolder of the repository it changes into the project first |
| `fwos baseline [--init]` | Adopt mode only: `--init` records today's findings and the checks that ran, so `fwos check` fails only on new ones. Without it, drops fixed findings and takes in a check that wasn't on when it was recorded; a check it covers only shrinks. `--init` refuses when the last commit has a baseline, and `fwos check` honours no more of a covered check than that commit's baseline holds. Gates, approvals, traceability, locked tests and the regression scope are never baselined |
| `fwos hash <path...>` | The content hash fwos records for each path |
| `fwos version` | The version (same as `--version`) |
| `fwos eject [--yes]` | Previews, then removes `.fwos/`, the hook, the fwos permission entry step 0 added, the `fwos-check` pin, scripts and CI step that run fwos, and the JUnit reporters that write to `.fwos/local/` (a line you changed, or a permission entry you wrote, stays and is listed, and while a line still writes there, so do the `.gitignore` lines); docs and code stay |

Approval targets: `brief`, `research`, `architecture` (modules.json), `design-system`, `fidelity`
(design-system/ and docs/app/reports/design-system.md, refused until a current gallery run is in
the report and every item is decided), `screens` (ia.json), `spec` (spec.md and test-plan.md
together), `acceptance`.

Routes: `code-only` (enters at build), `touches-ac` and `data-change` (spec), `new-feature`
(discovery), `design-system` (design-system), `add-platform` and `architecture` (architecture). In
an adopted app: `code-only` (build), and `touches-ac`, `new-feature` and `data-change` (spec).

Adoption levels, each including the ones before it: `checks` (`fwos check` with a baseline),
`design` (the app's own theme as tokens) and `delivery` (changes mapped onto the code, with a spec
and test delta, the spec gate on the app while a change is open, the team's tests run by
`fwos tests run`, and locked tests).

Steps, in order: discovery, research, architecture, design-system, screens, spec, build, accept, done.
