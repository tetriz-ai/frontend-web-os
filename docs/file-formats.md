# File formats

Every file fwos reads has a JSON Schema in the module that owns it. `fwos check` validates them
first and fails closed: an unsupported `schema` version stops every other check.

| File | Schema | What it holds |
|---|---|---|
| `.fwos/state.json` | [state.schema.json](../plugin/modules/state/schema/state.schema.json) | Schema version, mode, platforms, path overrides, and an adopted app's level with when each was set, and the stages its team keeps (`adopt.keep`, each with why and since when) |
| `.fwos/changes/<id>.json` | [change.schema.json](../plugin/modules/state/schema/change.schema.json) | One change: route, step, links to what it came from (a link with a `stage` is the team's own artifact for that stage), approvals (hashes, with the review a yes came from), skips, locked tests, unlocks, red runs, sign-offs, spend. An adopted app's change also holds `base`, the spec's criteria when it began, and `map`, what it touches in the code |
| `.fwos/manifest.json` | [manifest.schema.json](../plugin/modules/state/schema/manifest.schema.json) | Files fwos generates, with the checksum it last wrote |
| `.fwos/provenance.json` | [provenance.schema.json](../plugin/modules/state/schema/provenance.schema.json) | Files fwos wrote that became yours |
| `.fwos/baseline.json` | [baseline.schema.json](../plugin/modules/state/schema/baseline.schema.json) | Pre-existing findings (adopt mode) and the checks it covers, with the day each was recorded; a covered check only shrinks |
| `.fwos/quarantine.json` | [quarantine.schema.json](../plugin/modules/tests/schema/quarantine.schema.json) | Flaky tests, each with a reason, a name and an expiry date |
| `.fwos/slices/<change>/<slice>.json` | [slice.schema.json](../plugin/modules/build/schema/slice.schema.json) | What a slice built |
| `.fwos/local/runs/<states\|ia\|tests>/<target>.json` | [run.schema.json](../plugin/kernel/schema/run.schema.json) | One test of fwos's harness, or one run of the team's test script: what it saw, the revision it ran on and the harness that recorded it, if any (below) |
| `docs/app/modules.json` | [modules.schema.json](../plugin/modules/architecture/schema/modules.schema.json) | Modules, public entries, allowed dependencies |
| `docs/app/ia.json` | [ia.schema.json](../plugin/modules/screens/schema/ia.schema.json) | Pages, routes, nav, visibility, states |
| `docs/app/prototypes/<id>/bundle.json` | [bundle.schema.json](../plugin/modules/screens/schema/bundle.schema.json) | One feature's prototype bundle: its visual artifact, companions, state inventory, spec, decision record and intended IA (below) |
| `.fwos/prototypes.json` | Written by `fwos prototype promote`, schema 1 | Each promoted bundle: who promoted it, when, and the hash of each input it pinned |
| `design-system/design-system.json` | [design-system.schema.json](../plugin/modules/design-system/schema/design-system.schema.json) | Token files per mode, slot mapping, `[ASSUMED]` list, and for an import the copy of the theme it came from (`source`) |
| `design-system/components.json` | [components.schema.json](../plugin/modules/design-system/schema/components.schema.json) | The component registry with required states |
| `design-system/source/<file>` | The theme as it was, copied by `fwos design-system init --from-shadcn` and `fwos adopt --level design`, and named in design-system.json `source` | What the mapping report reads to say where each slot came from, even after the theme changes. Yours, like the rest of the folder |
| `docs/app/reports/design-system.md` | Markdown, generated by `fwos design-system report` | Every slot with the source file and key it reads, its original and resulting value in each mode and its status (preserved, approximated, defaulted, unsupported, changed), what the source had that nothing took, each component with its variants, states and interactions, the rendered comparison and the outcomes. The fidelity approval is a hash of it |
| `.fwos/fidelity.json` | [fidelity.schema.json](../plugin/modules/design-system/schema/fidelity.schema.json) | The decisions recorded with `fwos design-system decide`, each with its reason, who decided, when, and the hash of what it decided |
| `.fwos/local/results/fidelity.json` | Written by the gallery's Playwright run | Local evidence: each cell's computed-style differences, with the variables behind each, and each interaction's outcome on both sides. Screenshots go to `.fwos/local/gallery/` |
| `design-system/rules.yaml` | [rules-config.schema.json](../plugin/modules/rules/schema/rules-config.schema.json) | Rule overrides and custom rules |
| `docs/app/spec.md`, `test-plan.md` | Markdown blocks (below) | ACs and test cases |

## Versions and updates

Each file names the `schema` it was written against, and this release reads schema 1 of every one.
A file from any other schema fails the `state/schema` gate (`design-system/schema` too, for the
design system's two files), so every other check is OFF until it's fixed and nothing reads a file
it can't understand. The session start tells the agent the same.

The pack is the five files of yours that hold your product's choices: `design-system.json` with
its token files, `components.json`, `rules.yaml`, `ia.json` and `modules.json`.
[pack.ts](../plugin/kernel/pack.ts) lists them with the schema this release reads. Initialization,
scaffolding and design-system import can create these files. Once they are yours, those commands
do not overwrite them; `fwos update --yes` can migrate an existing file after its preview.

After a plugin update, `fwos update` previews two things and `fwos update --yes` does them: it
migrates a pack file or record from an older schema, and it refreshes `.fwos/cli/`, as
`fwos vendor` does. It copies each file it migrates, replaces or removes to
`.fwos/local/backup/<time>/` first. It writes nothing while a file is from a newer schema (upgrade
fwos), from an older one it has no migration for (rewrite it as schema 1, or keep the fwos that
wrote it), or was edited in `.fwos/cli/` since fwos wrote it.

No file has an older schema yet, so this release ships no migration, and no update has migrated a
real one: the migration step is tested with a stand-in. The first schema 2 ships with its
migration and a test on a file as the release before it wrote it.

## Approvals are hashes

```json
"approvals": {
  "brief": { "sha": "9f2c41d0ab12", "files": { "docs/app/brief.md": "9f2c41d0ab12" }, "by": "Ada", "at": "2026-10-07T10:00:00Z", "via": "chat" }
}
```

An approval holds while the files it covers hash the same. Line endings are normalised, so a
Windows checkout hashes like a Mac one. Docs record what they were built from in front matter:
`based_on: [brief.md@9f2c41d0ab12]` (written by `fwos stamp`).

## Markdown blocks

ACs in the spec and cases in the test plan are headings followed by `- Key: value` lines:

```markdown
### AC-reading-1: Saving a link puts it first
- Journey: J1
- Given an empty list, when I save https://example.com/a, then it's the first row.
- Proven against: local
- Release: first

### TC-reading-1: saving shows the new row first
- AC: AC-reading-1
- Level: component
- Platform: web
- Status: new
```

Named gaps are `### GAP-<n>: <title>` with `- Missing: <the access that's missing>`.

In an adopted app, a change's test plan also names the existing tests around it, one file per line,
or says there are none:

```markdown
## Regression scope

- app/(dashboard)/dashboard/team-members.test.tsx: the card's search and its empty state
- e2e/invite.spec.ts: only an owner can invite, on the same page
```

`### GAP-browser: <title>` with `- Missing:` stands in for a case in a browser when the app can't run
one yet, for a person to sign off.

## An adopted app's spec delta

A change in an adopted app traces its request to its criteria in the spec delta, with three more
blocks beside its criteria. `## Request` breaks the request into asks, each with the criteria that
deliver it or why it was left out. `## Open questions` asks each question with an ID, and its answer
goes under it: `fwos approve spec` refuses while one has none. `## States` lists the states of what
the change touches, each with the criterion that covers it, `unchanged`, or `none: <why>`:

```markdown
## Request
"add search and an empty state to the team members table"

### REQ-1: Search the team members
- AC: AC-team-members-1, AC-team-members-3

### REQ-2: Export the list as CSV
- Dropped: the app has no download route; a change of its own (Ada Lovelace)

## States
| State | What the user sees | Criterion |
|---|---|---|
| filtered-empty | No members match "<search>". | AC-team-members-2 |
| loading | the card's skeleton | unchanged |

## Open questions
### Q-1: Does a search match emails as well as names?
- Answer: Names and emails: a member with no name shows their email (Ada Lovelace)
```

A team that keeps its own practice for the idea stage needs no `## Request`, and one that keeps
design needs no `## States`. One that keeps its own spec writes only `## Acceptance criteria`, each
of the change's criteria with `- Source: <where in your spec>`, a link the change holds.

## Quarantine

```json
{ "schema": 1, "tests": [{ "match": "@AC-reading-4", "reason": "clock drift on CI", "by": "Ada", "until": "2026-11-01" }] }
```

`match` is part of a test name or an AC tag, matched as whole words, so `@AC-reading-4` never
matches `@AC-reading-41`. `until` is the last day the quarantine holds, as `YYYY-MM-DD`. An entry
with no date, or one fwos can't read, counts as expired.

## Test results

JUnit XML in `.fwos/local/results/` (the scaffold configures Vitest and Playwright to write there;
`paths.results` in state.json changes it). Test names carry `@AC-<id>`, `@state:<id>:<state>` and
`@TC-default-<row>` tags. `fwos tests run` writes them there from the team's own
scripts, and records each script's last run as a run record of kind `tests` (below): the command,
the runner, whether it ran in a browser, its exit code, its result files and how many tests passed,
failed and were skipped. A run whose results fwos can't read is recorded with why. Both are local
evidence, git-ignored like the rest of `.fwos/local/`.

## Harness runs

fwos's harness is two Playwright specs fwos writes into the app (`apps/web/e2e/fwos-states.spec.ts`
and `fwos-ia.spec.ts`, by `fwos harness` and the scaffold). Your `pnpm e2e` runs them with the rest.
Each test asks `fwos harness targets` what to render or open, and hands what it saw to
`fwos harness record`, which keeps it as one file per target:

```json
{
  "schema": 1,
  "kind": "states",
  "target": "page.list",
  "fwos": "0.1.0",
  "harness": { "file": "apps/web/e2e/fwos-states.spec.ts", "sha": "ce8da3d7d779" },
  "revision": "568cf0402b75",
  "config": { "server": "production build", "browser": "chromium 141.0.7390.37", "viewport": "1280x720" },
  "at": "2026-10-23T13:24:40.734Z",
  "observations": [{ "state": "loading", "status": 200, "found": true, "busy": 1, "alerts": [], "statuses": [], "items": [] }]
}
```

`revision` is a content hash of what a run of the app depends on: the app's folder (its tests, its
build output, fwos's docs and Markdown outside its source globs aside, for an app at the root too),
`packages/`, the design system, `ia.json` and the root package manifests and lockfile. So a Markdown
file the app reads at runtime from outside its source globs doesn't make a run stale. It is null
when they changed while the test ran. A check counts a record only while its revision is the current
one and its `harness.sha` is that of the harness this fwos ships, so a run of older code, or of an
edited harness, proves nothing. The edit tools can't write these files.

A state record's observations hold one entry per state: what renders inside the fixture's
`[data-fwos-fixture]` container (its text, elements marked busy, invalid or disabled, the text of
each alert and status, and its content items), and `hits`, what looked clickable there: its text,
what hovering it changed (`background-color`, `cursor: pointer`), the controls inside it, and what
a click away from them did (`nothing`, `navigated to /books/dune`, `changed the page`). An IA record's hold one role and flag setting: each
route it opened (status, where it ended, whether the not-found page rendered, whether a visible denial state alone rendered, the first redirect)
and every path the nav links to.

`fwos tests run` keeps a record of kind `tests` in `.fwos/local/runs/tests/` for each script it runs
in a project, replaced by the script's next run. Its target is the script, after its folder and
a `/` outside the root, its `harness` is null, its `config` holds the command fwos ran, and its
observations hold the run: `script`, `dir`, `display`, `command`, `runner`, `browser`, `mapped`,
`reason`, `exit`, `results` and `cases`. At acceptance it counts only while its application/test/runner inputs and exact produced result bytes match the record. `config.evidence` names the binding format, `testInputs` pins inputs, and each `result:<path>` holds a result SHA256; older unbound records require another `fwos tests run`. The acceptance report lists only current runs, and only current browser-run results count as browser evidence.

## Prototype bundles

A prototype bundle is one feature's handoff: a folder in `docs/app/prototypes/<id>/` whose
`bundle.json` links each part, every path from the project root.

```json
{
  "schema": 1,
  "id": "members",
  "title": "Members under /team",
  "pages": ["members"],
  "visual": [{ "kind": "figma", "ref": "https://www.figma.com/design/abc123/Members" }],
  "companion": [{ "kind": "route", "page": "members", "ref": "/fwos-screens/members" }],
  "states": "docs/app/prototypes/members/states.md",
  "spec": "docs/app/spec.md#members",
  "decision": "docs/app/decisions.md#D-4",
  "ia": "docs/app/prototypes/members/ia.json"
}
```

- `id` is the folder's name: one folder per feature. `pages` are the `ia.json` pages it adds or
  changes.
- `visual` is what it should look like, from any tool: `html` or `image` (a file in the
  repository), `figma`, `storybook` or `url` (an https link), or `route` (a path in the app).
- `companion` renders each page from registered components: a `route` in the app (the screens
  browser's `/fwos-screens/<page>`) or a `storybook` story, naming its `page`. A visual artifact
  alone can't be promoted.
- `states` is the state inventory: a `## <page>` section per page, then a `- <state>: what it shows`
  line for each of that page's states in the bundle's IA, no more and no fewer.
- `spec` and `decision` name a file, and a `#heading` (or, in a decisions table, the row whose first
  cell is the anchor, such as `#D-4`). A promotion pins that section or row, not the whole file.
- `ia` is the intended `ia.json`: the whole app as the feature leaves it, in the same format, with
  the roles and flags the project's `ia.json` declares. Every route the app has must be in it, as a
  nav, drill-down or redirect page, or unlinked with a reason.

No link may go into a `working/` folder, in the bundle or in the HTML and Markdown pages it links.
`fwos prototype promote` records the hash of each input in `.fwos/prototypes.json`, once each is
committed; `fwos prototype check` calls the promotion stale when one changes after that.
